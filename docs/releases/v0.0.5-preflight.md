# CLI v0.0.5 supervised production acceptance

## Decision and scope

The maintainer authorized `v0.0.5` as a one-time supervised production
acceptance of the corrected release transaction. A dedicated sandbox App was
not provisioned, and the production App private key must not be exported to a
sandbox. The exception therefore uses the official repository without weakening
its release environment, tag ruleset, immutable-release setting, or credential
isolation.

This record permits one `Native release and distribution` workflow dispatch for
version `0.0.5` from the exact reviewed `main` commit. It does not permit manual
tag or release creation, credential export, asset replacement, tag movement, or
version reuse. It does not mark the sandbox rehearsal complete and does not
apply to any later version.

## Why the immutable boundary is guarded

The workflow performs all building and packaging before requesting approval for
the `release` environment. The pre-approval jobs:

1. validate all npm and Rust versions and prove that the tag, GitHub release,
   and npm version are unused;
2. build and smoke-test four native targets;
3. build and test the exact npm tarball;
4. generate and validate Homebrew, WinGet, Scoop, and Chocolatey packages;
5. assemble one candidate, generate `SHA256SUMS` and
   `RELEASE-MANIFEST.json`, attest it, and retain it as the
   `harness-lens-v0.0.5-release` Actions artifact; and
6. expose the protected publication job for maintainer approval only after all
   preceding jobs succeed.

The publication job downloads that retained candidate and does not rebuild it.
It creates or reconciles a draft, uploads only manifest-declared files, verifies
the complete remote name, size, state, and SHA-256 inventory, and publishes only
an exact draft. It then requires GitHub to report `immutable=true`, the stable
tag at the original source SHA, and the unchanged asset inventory before npm or
the other distribution jobs may continue.

`SHA256SUMS` must validate all 13 packaged payload files. The release manifest
must identify repository `harness-lens/cli`, version `0.0.5`, tag `v0.0.5`, the
workflow's exact source SHA, workflow SHA, run ID, and run attempt. Its sorted
asset inventory must match every other candidate file, including `SHA256SUMS`.

## Mandatory operator gates

Before dispatch:

- verify the exact `main` commit has successful required CI and CodeQL checks;
- repeat the read-only audit of release immutability, default read-only workflow
  permissions, protected `release` and `npm` environments, stable-tag rules,
  environment-only App credentials, npm trusted publishing, and Homebrew tap
  protection;
- prove `v0.0.5` is absent from tags, releases and drafts, npm, crates.io, GHCR,
  and every enabled distribution destination; and
- dispatch `native-release.yml` once from `main` with input `0.0.5`.

Before approving the `release` environment:

- require every metadata, native, npm, Homebrew, Windows, and assembly job to
  succeed in the same run;
- download the retained candidate, require the exact inventory above, run
  `sha256sum -c SHA256SUMS`, and inspect `RELEASE-MANIFEST.json`;
- repeat the tag, release, draft, and npm absence checks to detect a race; and
- reject the deployment if any job, file, identity field, digest, setting, or
  external check is missing or conflicting.

Approval crosses the irreversible boundary. After approval, require the
published GitHub release to be immutable with the exact 15 assets and require
its tag to target the recorded source SHA. Approve the separate `npm`
environment only after those GitHub postconditions pass. Merge the generated
Homebrew formula PR only after its ARM64 and x86_64 checks pass; GHCR remains
blocked until that exact formula is merged and reverified.

## Failure handling

If a job fails before `release` approval, do not approve it and do not create a
tag or release manually. Fix the cause through a reviewed pull request and start
a new preflight run only while the version remains unused.

If publication is interrupted after a matching draft is created, do not start a
second release run, delete the draft, replace assets, or move the tag. Rerun the
failed job in the original workflow run so the transaction can reconcile only
the same provenance-bound draft and retained candidate. Stop for incident review
on any conflicting or already-published state.
